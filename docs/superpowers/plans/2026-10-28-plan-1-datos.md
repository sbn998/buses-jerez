# Plan 1: proceso de datos (horarios, paradas y recorridos)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un proceso diario en GitHub Actions que descarga de Comujesa líneas, paradas, horarios y recorridos, los valida y los publica como `data.json` + `manifest.json` en GitHub Pages. Si la validación falla, no publica nada y el workflow falla, y GitHub manda un correo al autor.

**Architecture:** Paquete Node/TypeScript independiente en `pipeline/`. Los parsers son funciones puras probadas con fixtures reales. `main.ts` las orquesta: descarga, ensambla, reconstruye viajes, valida contra la versión publicada anterior y escribe `pipeline/out/`. El workflow sube `out/` a Pages. El contrato de datos (`src/data/schema.ts`) vive en la app y el pipeline lo importa, así hay una sola fuente de verdad.

**Tech Stack:** Node 24, TypeScript, `tsx`, `vitest`, `cheerio` (HTML), `fast-xml-parser` (KML), GitHub Actions (`actions/upload-pages-artifact`, `actions/deploy-pages`).

**Spec:** `docs/superpowers/specs/2026-10-28-buses-jerez-design.md` (sobre todo 3.6, 4 y 4.1)

## Hoja de ruta (planes siguientes, no incluidos aquí)
1. **Este plan:** datos.
2. App base: development build, descarga y caché de datos, pestañas, i18n es/en, Horarios con calendario, Favoritos, avisos al abrir.
3. Mapas: mapa propio de Jerez (online y offline), Cerca de mí, Líneas, Recarga, Opciones, y cruce de paradas con OSM en el pipeline (solo warnings).
4. Cómo llego: búsqueda de lugares, intermediario de rutas a pie, planificador con 1 transbordo.
5. OCR de los PDF: viajes que no completan el recorrido, fechas de validez y avisos de cambio.
6. Publicación.

## Global Constraints
- Coste cero: ningún servicio con tarjeta. Solo GitHub (repo público `sbn998/buses-jerez`) y endpoints públicos sin clave.
- Nunca se suben claves de API ni información personal. `.gitignore` de lista blanca: cada carpeta nueva se añade explícitamente.
- Commits con `193912679+sbn998@users.noreply.github.com` (ya configurado en el repo local). Sin líneas de atribución.
- Si cualquier validación falla: **no se publica**, se conserva la versión anterior y el proceso sale con código ≠ 0.
- Peticiones a Comujesa: secuenciales, 250 ms entre peticiones, `User-Agent: buses-jerez-data/1.0 (+https://github.com/sbn998/buses-jerez)`, 3 reintentos con espera de 2 s, 4 s y 8 s.
- Base: `https://www.comujesa.es`. Líneas `1`…`18`.
- URL pública de datos: `https://sbn998.github.io/buses-jerez/` (`manifest.json`, `data.json`).
- Coordenadas en orden GeoJSON `[lon, lat]`. Horas como texto `"HH:MM"`.

## Review Focus
1. **Viajes que empiezan a mitad de recorrido** (el primer bus de la línea 1 empieza en Constitución a las 7:10). Deben quedar como viajes propios, no pegados al siguiente. Lo prueba la Task 6.
2. **La web de Comujesa responde HTML vacío o una página de error con código 200** (pasa con TYPO3). Una línea sin paradas o una parada sin horas tiene que bloquear la publicación, no publicarse vacía. Lo prueba la Task 8 (`rejects line with no stops`, `rejects stop with no times`).
3. **Códigos de parada que no cuadran entre fuentes** (Madre de Dios: 280 en el mapa y 352 en el buscador). La parada tiene que acabar con coordenadas por coincidencia de nombre u override, o bloquear la publicación. Nunca debe salir con coordenadas 0,0. Lo prueban las Tasks 5 y 8.
4. **Caída parcial**: Comujesa devuelve bien 17 líneas y una falla tras los reintentos. No se publica un dataset con 17 líneas. Lo prueba la Task 8 (`rejects missing line`).
5. **Primera ejecución sin versión anterior publicada** (404 en `data.json`). Debe publicar si el resto de la validación pasa. Lo prueba la Task 8 (`accepts when previous is null`).
